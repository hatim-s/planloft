# Migrate a legacy theme

This is an agent-guided, one-way migration. There is no legacy-theme migration CLI or
backwards-compatible template/layout support. Back up the original theme and every
affected source before changing them. Preserve authored Markdown and MDX content,
comments, scripts, and stable task keys. Inspect the legacy template, layout, and CSS
alongside representative rendered documents.

Create a separate theme directory under the effective Planloft home with a new, unused
candidate name. Put only a token-based `style.css` there. Convert palette and font
values using the public variables in the `planloft-customise` theme reference or an
existing resolved theme's CSS. Do not resolve the legacy theme: the runtime rejects its
`template.md`, `template.mdx`, or `layout.html`. Arbitrary structural CSS cannot be
automatically converted to tokens. Where needed, move legacy layout or structural CSS
into copies of the affected documents' HTML or MDX author code, preserving behavior.

Review the candidate and document copies, then render representative copies with
`planloft render <source> --theme <candidate-name> --out <temporary-directory>`.
Use the appropriate trust flags and check both light and dark modes. Keep the original
theme and documents unchanged until this review and rendering succeed. Then promote the
reviewed candidate CSS to the original theme name, remove the original legacy assets,
and apply the reviewed document changes. Keep the backups and candidate until the
replacement has been checked. If validation fails, revise the candidate and repeat.


## Legacy rendered HTML

Old compiled HTML may contain unmarked Planloft controls and theme styles. The current
renderer rejects conflicting controls rather than removing unknown authored content.
Regenerate from the original Markdown or MDX when available. If only the old HTML
artifact remains, back it up and work on a candidate copy. Identify and remove only
controls, scripts, and theme styles verified to be generated by the old renderer;
preserve author code. Never blindly delete content using a marker regex. Render the
candidate and compare it with the original before replacing anything.

# Migrate a document

The existing `planloft migrate` command converts eligible Markdown to MDX or copies HTML. It does not migrate themes.

Find the installed CLI with `command -v planloft` and check `planloft help migrate`.
A skill-only installation does not install the CLI. If this command is absent, report
that the installed version needs an upgrade; do not assume a source checkout or run a
script relative to the current working directory.

Run the installed tool with explicit paths, then inspect the output before using it:

```sh
planloft migrate ./proposal.md --out ./proposal.mdx --dry-run
planloft migrate ./proposal.md --out ./proposal.mdx
```

The dry run validates the conversion and checks the destination and `proposal.md.bak`
without writing. A write creates the backup alongside the source and refuses to
replace different destination or backup contents. If the destination already matches
but its backup is missing, a dry run reports `dry-run-backup` and a write creates the
backup and reports `backup-created`. A repeat with both files matching is unchanged.
Markdown conversion retains frontmatter, code, links and GFM syntax. The MDX renderer
must support GFM. The migration checks syntax without executing MDX.

If a diagnostic identifies raw HTML, inspect the indicated source location. Preserve
scripts, styles, and layout in HTML when their behavior matters. For static markup,
replace it with equivalent Markdown or a reviewed MDX component, then migrate a
separate edited source. For example, replace `<strong>Warning</strong>` with
`**Warning**`; do not make that replacement if markup has attributes or behavior that
must survive. For an existing HTML document, retain the format:

```sh
planloft migrate ./page.html --out ./page-copy.html --dry-run
planloft migrate ./page.html --out ./page-copy.html
```

Review any other MDX parse diagnostic at its reported location; do not drop content
just to make conversion pass. Do not overwrite an unrelated file or backup. The tool
does not migrate `.mdx` sources or their compiled bundles.

Migration does not enable collaboration. Attach it only when requested, using the
existing attachment command and a stable document identity. Reattachment retains that
identity. GFM task lists are static; for shared state, replace them deliberately with
`<Todo task="stable-key" label="Task text" />` and assign stable keys. Do not derive keys
from task text.
Keep service credentials on the server. MDX and compiled snapshots execute code;
use `--trusted-mdx` only for sources, dependencies, registries and snapshots the user
trusts. Re-hoist edited stored MDX from its original dependency context.
