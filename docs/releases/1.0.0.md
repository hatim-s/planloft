# Planloft 1.0.0

Status: prepared, not published. The repository and package version are 1.0.0.
The maintainer publishes
from a clean `main` with `bun run release 1.0.0`. Until then, `planloft@1.0.0` does not
install.

## What changes

- **MDX documents.** `.mdx` sources with built-in components, local imports, and
  component registries. MDX is executable, so render, hoist, and publish require
  `--trusted-mdx`. See [ADR-0018](../adr/0018-trusted-mdx-snapshots.md).
- **Built-in components.** Callout, Stat, Status, Badge, Checklist and Todo, Timeline,
  DataTable, and line, bar, donut, waterfall, heatmap, and sparkline charts. They
  render static HTML and SVG. The browser gets no React, only a small reader script for
  the theme toggle and chart tooltips. See [components](../components.md).
- **Token-only themes.** A theme is one `style.css` of `--planloft-*` variables. The six
  built-in themes were redesigned. See
  [ADR-0019](../adr/0019-token-only-themes-and-html-support-blocks.md).
- **Themed trusted HTML.** Trusted HTML now gets the theme CSS and reader controls in
  two owned blocks. The rest of the authored HTML is kept byte for byte.
- **Collaboration.** Opt-in comments, shared notes, and shared tasks for HTML documents,
  with generated services for Cloudflare (D1), Vercel (Turso), and local Node (SQLite).
  See [ADR-0020](../adr/0020-collaboration-service-and-client.md) and
  [deployment](../deployment.md#collaboration-service).
- **`planloft migrate`.** One-way Markdown to MDX conversion with a backup, plus a
  same-extension HTML copy with a backup.
- **`planloft gallery`.** A local gallery of themes and components.

## Breaking changes

| Change | What breaks | What to do |
| --- | --- | --- |
| Node.js 22.15.0 or newer | The CLI and the local collaboration service no longer support Node 18 or 20. | Upgrade Node before installing 1.0.0. Bun 1.4 or newer also works. |
| Themes are tokens only | A custom theme with `template.md`, `template.mdx`, or `layout.html` is rejected at resolution. | Migrate the theme by hand to a token-only `style.css`. See [legacy theme migration](../installation-migration.md#legacy-theme-migration). |
| Trusted HTML output changes | Rendered HTML now contains Planloft's head and controls blocks. Old rendered HTML with unmarked controls from an earlier renderer is rejected. Frameset HTML is rejected. | Re-render from source where you can. Otherwise follow [legacy rendered HTML](../installation-migration.md#legacy-rendered-html). |
| Prepared hoist | `hoistDocument(document)` no longer takes a canonical document straight from `ingestDocument`. | Call `prepareDocument(document, { sourcePath, projectRoot })` and pass its result to `hoistDocument`. |
| Application errors | Operations on `createPlanloftApplication()`, including MDX and migration, report problems only through `PlanloftApplicationError` with a `diagnosticCode`, plus the component and source location when known. Lower-level exports such as `compileMdx` and `prepareDocument` can still throw `MdxAuthoringError`. | Switch on `diagnosticCode` for application calls. Do not parse messages. |
| Stricter component input | Invalid number formats and malformed currency codes, repeated bar categories or donut labels, repeated heatmap cells, and repeated waterfall labels are authoring errors. | Fix the reported component input. |

If you ran a pre-release build of this branch, these changes also apply.
`attachCollaboration(html, config)` no longer takes client asset paths.
`RenderOptions` no longer has `bodyHtml` or `extraStyles`. MDX and migration errors
from `createPlanloftApplication()` operations are now `PlanloftApplicationError`
instead of separate classes; the lower-level MDX exports keep `MdxAuthoringError`. Collaboration bodies are capped at 4096 UTF-16 code units instead of
100,000 characters. Pre-release MDX snapshots are unminified. Stored preview and deploy
still read them. Hoist those documents again from source to get a minified 1.0.0
snapshot.

The 1.0.0 version itself does not change stored documents, configuration, or hosting
repositories on install.

## Before you upgrade: backups

Copy these before installing 1.0.0, so you can roll back:

1. The Planloft home, `~/.planloft` or `$PLANLOFT_HOME`: configuration, stored
   documents, MDX snapshots, user themes, and component registries.
2. Any project `.planloft/` directory with copied documents or a component registry.
3. Custom theme directories, if you will migrate them.
4. For collaboration, a database export of your D1 or Turso data before applying the
   new migration. The migration trims each note's history to its latest 20 revisions,
   and that cannot be undone without the export.

The hosting repository is in Git, so its history is its backup.

## Upgrade

Follow the [installation migration guide](../installation-migration.md). In short:
upgrade Node, install `planloft@1.0.0` once it is published, run `planloft init` and
`planloft config` to validate, migrate custom themes, and hoist MDX documents again
from source when you want the new component output. Stored MDX snapshots are pinned
and keep rendering as they were compiled.

`planloft migrate` stays one-way. It writes a `.bak` beside each source and never
replaces a different destination or backup.

## Rollback

1. Reinstall the previous CLI: `npm install -g planloft@0.5.0` (or your earlier
   version). That version needs the Node it supported.
2. Restore the Planloft home and project `.planloft/` backups. 0.5 has no MDX
   support, so MDX documents and snapshots created by 1.0.0 do not render there.
3. If you deployed a rebuilt collaboration service, redeploy the previous service and
   restore its database export. Attached HTML that expects the new client must be
   re-attached or rolled back with it.
4. Hosting repositories migrated to the shared `public/` layout stay migrated; that
   migration has no reverse command. Use Git history if needed.

## Collaboration access, stated plainly

There are no viewer accounts. Anyone who can open an attached page can read all
comments and notes, add comments, delete any comment or thread, create and edit notes,
and tick shared tasks. Notes cannot be deleted. The admin token only registers
documents and stays on the server. Readers see other readers' changes after a reload;
there is no polling. Per-document caps limit live threads, replies, notes, task keys,
creation identities, text length, and note history. See
[deployment](../deployment.md#collaboration-service) for the numbers.

Two `Todo` components with the same `task` key are one shared task. They share a
checked state and get distinct HTML ids.

## Release plan

Gates run against the final `main` commit, before `bun run release 1.0.0`:

1. **Source.** `bun run typecheck` and `bun run test` pass.
2. **Supported runtime.** The maintainer runs the suite on Node 22.15.0, the declared
   minimum, and on Bun 1.4, then checks the packed tarball on exactly Node 22.15.0:

   ```sh
   bun scripts/validate-packed-package.ts <tarball> --minimum-node
   ```

   With `--minimum-node`, the check fails unless `node` on `PATH` is `v22.15.0`.
3. **Clean package consumer.** `scripts/validate-packed-package.ts` installs the
   packed tarball with production dependencies only into a disposable directory, runs
   the CLI, imports the public API and `planloft/components`, and typechecks a small
   consumer. The release command runs it without the flag:

   ```sh
   bun scripts/validate-packed-package.ts <tarball>
   ```

   That form accepts any stable Node 22.15.0 or newer on `PATH`, so the release can run
   on a newer supported Node. Gate 2 covers the exact minimum.
4. **Provider bundles.** `planloft collaboration-build` for `local`, `cloudflare`, and
   `vercel` produces importable bundles. This proves bundling only, not hosted
   acceptance.
5. **Browser flows.** On a rebuilt gallery and an attached document: theme toggle, chart
   keyboard and tooltips, comment create, reply, resolve, and delete with focus
   checks, notes, and shared tasks.
6. **Docs.** README, skills, and this file match the shipped behavior.

`bun run release 1.0.0` then repeats its own checks, publishes, tags `v1.0.0`, and
verifies the released skills. See the [release guide](../releasing.md). The maintainer
runs it. Agents do not publish.
